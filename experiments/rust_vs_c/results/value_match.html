Value-Based Block Match Accuracy: Rust vs C

Core Question: When an O0 block and O2 block from the same function are paired, do they compute the same thing? We verify this by running each block with 4 concrete test input sets and checking if they produce identical register outputs. A match is correct only if the blocks produce overlapping concrete values — not by structural similarity or callee names.

Method: Value-Based Match Correctness

Problem with the old approach: The previous analysis used structural similarity (opcodes, callee names, instruction count). Callee names are completely unstable across optimization levels — a call Vec::push at O0 becomes inlined arithmetic at O2. Structural similarity scores are meaningless: a 0.7 doesn't mean 70% correct.

What we do instead

Step 1: Micro-Execute Each Block
// 4 test input sets seed registers:
Set 0: [0x41, 0x42, 0x43, 0x44, ...]  // small distinct
Set 1: [1, 2, 4, 8, 16, 32, ...]       // powers of 2
Set 2: [0x1000, 0x2000, 0x3000, ...]    // larger values
Set 3: [0xFF00, 0xFE00, 0xFD00, ...]    // high bits

// For each block: execute, collect output registers
Block 0x446697 → {arg0: [0x0], arg1: [0x0], ret0: [0x0]}
Block 0x42314f → {arg0: [0x0], arg1: [0x0], ret0: [0x0]}
                  ↑ Same outputs = same computation
Step 2: Match by Value, Not Structure
// Similarity = weighted combination of VALUE features:
concrete_outputs:  50%  ← the gold signal
dataflow_edges:    25%  ← which regs feed which
memory_pattern:    15%  ← what gets read/written
constants:         10%  ← embedded immediates

// A match is CORRECT if value_sim ≥ 0.3
// This means: blocks share real computational overlap
// NOT: "opcodes look similar" or "same function called"

Why concrete values work

If O0 block A and O2 block B both take register inputs [0x41, 0x42] and produce output ret0=[0x83], they're computing the same addition — regardless of whether one uses add rax, rbx and the other uses lea rax, [rdi+rsi]. Optimization changes how a value is computed but not what is computed. Concrete values capture this invariant.

fn bc_07(data: &[u64]) -> Vec<i64> {
    let n = data.len();
    if n < 3 { return vec![]; }
    let mut result = Vec::with_capacity(n - 2);
    for i in 1..n - 1 {
        // data[i-1], data[i], data[i+1] each generates:
        //   cmp rdi, rsi; jae panic_bounds_check
        let val = -(data[i-1] as i64)
                + 2 * data[i] as i64
                - data[i+1] as i64;
        result.push(val);
    }
    // Second pass: smooth
    for i in 0..result.len() {
        let left = if i > 0 { result[i-1] } else { result[i] };
        let right = if i+1 < result.len() { result[i+1] } else { result[i] };
        smoothed.push((left + result[i] + right) / 3);
    }
    smoothed
}

int64_t *bc_07(const uint64_t *data, size_t n, size_t *out_len) {
    *out_len = 0;
    if (n < 3) return NULL;
    size_t rlen = n - 2;
    int64_t *result = malloc(rlen * sizeof(int64_t));
    for (size_t i = 1; i < n - 1; i++) {
        // No bounds checks — raw pointer arithmetic
        result[i-1] = -(int64_t)data[i-1]
                    + 2*(int64_t)data[i]
                    - (int64_t)data[i+1];
    }
    int64_t *smoothed = malloc(rlen * sizeof(int64_t));
    for (size_t i = 0; i < rlen; i++) {
        int64_t left = (i > 0) ? result[i-1] : result[i];
        int64_t right = (i+1 < rlen) ? result[i+1] : result[i];
        smoothed[i] = (left + result[i] + right) / 3;
    }
    free(result);
    return smoothed;
}

Why Rust Wins: Bounds Checks Create Value-Stable Anchors

Rust's bounds checks generate cmp + jae blocks at O0 AND O2. Even though the optimizer eliminates many redundant checks, the remaining ones produce the same comparison values (array length vs index). These blocks output the same concrete register values across optimization levels because the comparison semantics are preserved.

C has no bounds checks → no anchor blocks. The optimizer freely restructures the entire loop body, fusing the convolution arithmetic into different register assignments. Without anchor blocks, every O2 block computes values in a completely different register allocation.

Why Rust catastrophically fails: Rust's match on an enum compiles to a jump table (jmp rax) that dispatches based on the discriminant tag. angr's CFGFast cannot follow indirect jumps — it only resolves direct call/jump targets. Result: the entire function body (hundreds of instructions) appears as 1 giant block at O0. At O2, some match arms are inlined/simplified, producing only 1 block too — but a completely different one. With 1 O0 block vs 1 O2 block, there's exactly 1 match attempt, and the values don't overlap at all.

Why C wins: C's switch compiles to cascading cmp + je at O0 — each case is a separate block with direct jumps. angr resolves all 82 blocks correctly. At O2, the compiler can fuse some cases but the comparison values (tag constants, literal values) remain stable. 16 of 66 matched blocks produce the same concrete outputs.

fn iter_16(data: &[u64], group_size: usize) -> u64 {
    if group_size == 0 { return 0; }
    let groups: Vec<&[u64]> = data.chunks(group_size).collect();
    let group_sums: Vec<u64> = groups.iter()
        .map(|g| g.iter().sum()).collect();
    let group_maxes: Vec<u64> = groups.iter()
        .map(|g| g.iter().max().copied().unwrap_or(0)).collect();
    let total: u64 = group_sums.iter()
        .zip(group_maxes.iter())
        .map(|(&s, &m)| s.wrapping_add(m)).sum();
    total
}
C
uint64_t iter_16(const uint64_t *data, size_t len,
                  size_t group_size) {
    uint64_t total = 0;
    for (size_t i = 0; i < len; i += group_size) {
        size_t end = (i + group_size < len) ?
                     i + group_size : len;
        uint64_t sum = 0, max = 0;
        for (size_t j = i; j < end; j++) {
            sum += data[j];
            if (data[j] > max) max = data[j];
        }
        total += sum + max;
    }
    return total;
}
Why Rust wins despite "iterator sugar": This is NOT about the iterator syntax. It's about what chunks() compiles to at the binary level.

chunks(group_size) generates a loop with bounds checking: cmp remaining_len, group_size; jae take_full_chunk. These boundary comparison blocks produce the same concrete values at O0 and O2 because the comparison (remaining data length vs chunk size) is semantically preserved.

The 3 separate .collect() calls also generate Vec allocation patterns (capacity check → alloc → store) that produce recognizable value patterns across optimization levels.

Why C loses: C fuses the sum and max computation into a single loop body. At O0 this is 14 blocks. At O2, the compiler merges the inner loop into 10 blocks with completely different register assignments. The fused computation has no "anchor" blocks — every block does a mix of sum and max updates, and the optimizer reorders everything.

uint64_t iter_12(const uint64_t *data, size_t len,
                  uint64_t threshold) {

    uint64_t acc = 0;
    for (size_t i = 0; i < len; i++) {
        acc += data[i]; running[i] = acc;
    }
    uint64_t crossings = 0;
    for (size_t i = 0; i < len - 1; i++) {

            crossings++;
    }

}
Why Rust wins: windows(2) generates bounds-checked access to w[0] and w[1]. The concrete values from the comparison (flags set by the cmp instruction, the threshold constant) are preserved.

Why C loses: C's running[i] is unchecked pointer arithmetic. The accumulation loop and the crossing-count loop are separate at O0 but merged at O2 (the compiler deduces that running[i+1] - running[i] == data[i+1]). This algebraic optimization changes what intermediate values exist, destroying value continuity.

fn opt_04(data: &[u64], target: u64) -> Option<(usize, u64)> {
    let win_size = 3;
    for start in 0..data.len() - win_size + 1 {
        let mut all_above = true;
        let mut win_sum = 0u64;
        for j in 0..win_size {
            let val = data.get(start + j)?;  // ? = early return None
            win_sum += val;
            if *val <= target { all_above = false; }
        }
        if all_above { return Some((start, win_sum)); }
    }
    None
}
C
int opt_04(const uint64_t *data, size_t len,
           uint64_t target, size_t *out_start,
           uint64_t *out_sum) {
    for (size_t s = 0; s + 3 <= len; s++) {
        int all_above = 1;
        uint64_t wsum = 0;
        for (size_t j = 0; j < 3; j++) {
            wsum += data[s + j];
            if (data[s + j] <= target) all_above = 0;
        }
        if (all_above) { *out_start = s; *out_sum = wsum; return 1; }
    }
    return 0;
}
Why C wins: C's simple for loop with direct array access compiles to a tight loop at O0 with a clear comparison block. At O2, the compiler unrolls the inner j-loop (since win_size=3 is constant), but the comparison against target is still present with the same semantics. The concrete values from data[s+j] <= target are stable.

Why Rust loses: The ? operator on data.get(start+j) compiles to:
  1. Call slice::get() → returns Option<&u64> (discriminant + pointer)
  2. Check discriminant: if None, propagate None up the call stack
  3. Unwrap the Some variant to get the pointer
At O0, this generates 32 blocks (9 per ? invocation: call + check + branch + unwrap + ...). At O2, the compiler proves that get() never returns None (because the loop bounds ensure validity) and eliminates the entire Option machinery, replacing it with direct array indexing. The 32 O0 blocks collapse to 9 O2 blocks. The Option-handling blocks at O0 have no counterpart at O2 — they're dead code that was optimized away. Their concrete values have no match target.

fn opt_09(data: &[u64], target_sum: u64) -> Option<(usize, usize)> {
    if data.len() < 2 { return None; }
    let mut lo = 0;
    let mut hi = data.len() - 1;
    while lo < hi {
        let left = data.get(lo)?;
        let right = data.get(hi)?;
        let sum = left.wrapping_add(*right);
        if sum == target_sum { return Some((lo, hi)); }
        else if sum < target_sum { lo += 1; }
        else { hi -= 1; }
    }
    None
}
C
int opt_09(const uint64_t *data, size_t len,
           uint64_t target_sum, size_t *lo_out, size_t *hi_out) {
    if (len < 2) return 0;
    size_t lo = 0, hi = len - 1;
    while (lo < hi) {
        uint64_t sum = data[lo] + data[hi];
        if (sum == target_sum) {
            *lo_out = lo; *hi_out = hi; return 1;
        } else if (sum < target_sum) lo++;
        else hi--;
    }
    return 0;
}
Same pattern as opt_04: The ? operator generates Option-checking blocks at O0 that are completely eliminated at O2. The ? operator pattern: Every data.get(idx)? generates ~4 extra blocks at O0 (call get, check discriminant, branch on None, unwrap Some). At O2, the compiler proves these are always Some and deletes the blocks entirely. This creates an asymmetric block count (32 O0 → 9 O2) where most O0 blocks are dead-code artifacts.

The method chain problem: Rust's functional style (.find().map().filter().unwrap_or()) creates a chain of monomorphized generic function calls at O0. At O2, LLVM inlines and fuses them all. The O0 blocks are defined by call instructions to specific generic instantiations. The O2 blocks are defined by inlined arithmetic. There is no value overlap because the computation is restructured from "process Option at each step" to "compute the final value directly."

Why Rust wins: Rust's a[i] and b[j] indexing generates bounds checks: cmp i, a.len(); jae panic. These comparison blocks are present at both O0 and O2. The merge loop body has comparisons against array lengths that produce the same concrete values.

Additionally, the ownership system means a and b are consumed (moved into the function). At O0, Rust generates drop_in_place<Vec<u64>> calls for the input vectors. At O2, these become inlined deallocation sequences. Both versions compute the same "pointer + capacity → dealloc" pattern with matching concrete values.

Why C is close but loses: C's merge loop is actually very similar, but the free(a)/free(b) calls at O0 become a single combined deallocation pattern at O2 that the compiler optimizes differently. The running max pass in C is also fused into the merge at O2, changing the block boundaries.

uint64_t own_04(uint64_t n) {
    typedef struct Node { uint64_t val; struct Node *next; } Node;
    Node *head = NULL;
    for (uint64_t i = n; i > 0; i--) {
        Node *node = malloc(sizeof(Node));
        node->val = (i-1)*(i-1) + 1;
        node->next = head; head = node;
    }
    uint64_t sum = 0, count = 0;
    for (Node *cur = head; cur; cur = cur->next) {
        sum += cur->val; count++;
    }
    // manual free loop
    while (head) { Node *t = head; head = head->next; free(t); }
    return sum * count;
}
Why C wins: C's linked list traversal is a simple pointer-chasing loop: cur = cur->next. At both O0 and O2, the loop body reads two fields (val, next) and accumulates. The concrete values from the accumulation (sum += val, count++) are preserved.

Why Rust loses: Rust's Box<List> generates recursive Drop. When head goes out of scope, the compiler generates drop_in_place<List> which recursively frees each Cons node. At O0: this is a chain of call drop_in_place<List> blocks. At O2: LLVM converts the recursive drop into an iterative loop (tail-call optimization), producing completely different blocks. The recursion-to-iteration transformation changes the concrete values (stack frame layout vs register-based iteration).

Additionally, the match on List has the same jump-table problem as em_06, reducing the traversal loop to fewer analyzable blocks.

Key Findings

Finding 1: Bounds checks are the ONLY Rust feature that consistently helps matching.
Rust's array bounds checks (cmp index, length; jae panic) create blocks that compute the same comparison at both O0 and O2. Even when the optimizer eliminates redundant checks, the remaining ones are value-stable. This gives Rust a consistent edge in the bounds_check category (23% vs 17%).
Finding 2: The ? operator and Option method chains HURT matching.
Every ? generates ~4 extra blocks at O0 for Option discrimination. At O2, the compiler proves these are always Some and eliminates them entirely. The O0 blocks have no O2 counterpart → match accuracy drops. Method chains (.find().map().filter()) are even worse: N function calls at O0 → 1 fused loop at O2.
Finding 3: Rust match on enums is catastrophic for static analysis.
match compiles to jump tables (jmp rax). angr's CFGFast cannot resolve indirect jumps. Result: entire function bodies appear as 1-2 blocks instead of dozens. C's equivalent switch often uses cascading if/else, which is fully analyzable. em_06: Rust 0% (0/1) vs C 24.2% (16/66).
Finding 4: Ownership/Drop has a mixed effect.
Simple ownership (move semantics, Vec deallocation) slightly helps because the dealloc pattern is value-stable. But Box-based recursive data structures hurt because LLVM converts recursive Drop to iterative loops at O2, completely changing the concrete execution values.
Finding 5: More blocks ≠ worse matching (it's the opposite).
Rust consistently generates more O0 blocks than C (due to bounds checks, Option handling, Drop calls). More blocks means more matching candidates. Even at low per-block accuracy (20-30%), the absolute number of correct matches can be higher. The real problem is when blocks collapse (99 O0 → 1 O2 due to inlining, or 1 O0 due to jump tables).

Bottom line for binary diffing tool design:
When matching Rust binaries across optimization levels, lean heavily on concrete execution values from bounds-check and comparison blocks. Avoid relying on callee names (they vanish at O2) or structural features (block counts change drastically). The value-stable "anchor blocks" from Rust's safety checks are the most reliable signal for cross-optimization matching.

For Rust code that uses match on enums, consider augmenting static CFG analysis with dynamic tracing or symbolic execution that can resolve jump tables.

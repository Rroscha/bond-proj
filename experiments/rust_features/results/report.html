Rust vs C: Which Language's Binary Code Is Easier to Match?

The question: When a compiler optimizes code (O0 → O2), it rearranges the machine instructions. Can we still figure out which parts of the optimized code correspond to which parts of the original? And does Rust or C make this easier?

Why it matters: Binary diffing (matching code across versions) is essential for security analysis, malware detection, and patch analysis. If a language's compiler generates code that's hard to match after optimization, it's harder to analyze.

What we did: We wrote 100 functions in Rust and 100 semantically equivalent functions in C (same algorithm, same logic), compiled each at O0 (no optimization) and O2 (full optimization), then tried to match the basic blocks between O0 and O2 using 3 different methods.

The 5 Rust features we test (20 functions each):

  1. Bounds Checking (bc_) — Rust auto-checks array indices; C does not
  2. Ownership & Move (om_) — Rust moves values instead of copying pointers
  3. Drop Glue / RAII (dg_) — Rust auto-generates destructor code; C requires manual free()
  4. Option/Result + ? (qm_) — Rust's error propagation generates discriminant checks
  5. Panic Paths (pu_) — Rust's unwrap/expect generate hidden panic blocks

Why Rust is expected to be harder: Each of these features makes the Rust compiler generate extra basic blocks that have no equivalent in C (bounds checks, drop calls, panic paths, discriminant branches). At O2, the compiler eliminates, merges, or inlines many of these extra blocks. This means the O0→O2 block structure changes much more dramatically for Rust than for C, making matching harder.

How we know if a match is correct (ground truth): We compiled all binaries with debug=2 to include DWARF debug information — a standard format that records which source code line each machine instruction came from. Using this mapping, we can check any pair of blocks: if the O0 block and O2 block were compiled from at least one shared source line, they are a "true match." Otherwise the match is wrong. This gives us real accuracy rather than guessing based on similarity scores.

How Block Matching Works (30-second version)

A basic block is a straight-line chunk of assembly instructions with no branches in the middle. A function is made of many basic blocks connected by jumps.

When the compiler optimizes (O0 → O2), it rearranges, merges, and eliminates blocks. Our job: figure out which O2 block corresponds to which O0 block.

We try 3 methods:

  1. Value-based: Run each block with test inputs. If two blocks produce the same output values, they probably do the same thing. (Like testing a function with sample inputs.)
  2. Opcodes: Compare the set of instruction types (add, mov, cmp, call, etc.) using Jaccard similarity: overlap / union. If O0 has {mov, cmp, add} and O2 has {mov, cmp, jmp}, they share 2 out of 4 unique opcodes → similarity = 2/4 = 50%.
  3. Constants: Compare the numeric constants embedded in the instructions, also using Jaccard similarity. If both blocks use the numbers 8 and 16, but only O0 has 0xFF, similarity = 2/3 = 67%.

For each method, we use the Hungarian algorithm to find the best one-to-one matching between O0 and O2 blocks. If one side has more blocks (say 43 O0 vs 45 O2), the algorithm produces min(43, 45) = 43 pairs; the extra blocks on the larger side go unmatched.

Then we check each pair against DWARF ground truth: using debug info, we know which source code line(s) each block was compiled from. If the O0 block and O2 block share at least one source line, the match is correct. Otherwise it's wrong.

Accuracy = (number of correct pairs) / (total pairs produced by Hungarian). For example, if 5 out of 12 pairs share source lines, accuracy = 5/12 = 42%. Unmatched blocks (surplus on either side) are not counted as wrong — they simply have no partner.

What does "sim=0%" mean? When two blocks share zero features (no opcodes in common, or neither has constants, or neither produces execution output), the similarity score is 0%. The algorithm still pairs them because Hungarian must assign every block on the smaller side to something — even if the best available match is terrible.

Bounds Checking: bc_01 — Binary search on a slice

What is this feature?

Rust automatically checks that every array index is within bounds. When you write data[i], the compiler inserts a hidden check: "is i less than data.len()?" If not, the program panics instead of reading garbage memory.

C does not check. data[i] just reads whatever is at that memory address, even if i is out of range. This means C code has fewer instructions, but also fewer safety guarantees.

How does this affect binary matching? Let's look at bc_01 — a binary search function. Both Rust and C implement the same algorithm, but the compiled code looks very different.

Step 1 — Source Code: What the programmer writes

Rust
/// Binary search with explicit indexing
#[inline(never)]
fn bc_01(data: &[u64], target: u64) -> Option<usize> {
    let mut lo = 0usize;
    let mut hi = data.len();
    while lo < hi {
        let mid = lo + (hi - lo) / 2;
        if data[mid] == target { return Some(mid); }
        else if data[mid] < target { lo = mid + 1; }
        else { hi = mid; }
    }
    None
}
C
/* =========================================================================
   BOUNDS CHECKING (bc_01 .. bc_20)
   C: raw pointer arithmetic, no checks.
   ========================================================================= */

NOINLINE int bc_01(const uint64_t *data, size_t n, uint64_t target, size_t *out_idx) {
    size_t lo = 0, hi = n;
    while (lo < hi) {
        size_t mid = lo + (hi - lo) / 2;
        if (data[mid] == target) { *out_idx = mid; return 1; }
        else if (data[mid] < target) lo = mid + 1;
        else hi = mid;
    }
    return 0;
}

Step 2 — What the compiler does to the code

Before looking at the matching results, we need to understand how the compiler transforms this source code into machine instructions, and what changes between O0 and O2.

Rust

The Rust compiler turns data[mid] into:

  1. cmp rax, rsi — compare index mid with data.len()
  2. jae panic_bounds_check — if mid ≥ len, jump to panic code
  3. mov rax, [rdi + rax*8] — only if the check passes, read the value

Each bounds check creates an extra basic block (the cmp+jae instructions). At O0, Rust has 25 basic blocks. Many of these are bounds check blocks.

At O2, the compiler eliminates some redundant checks but keeps the ones it can't prove safe. Result: 12 blocks. (DWARF maps 19/25 O0 blocks to source lines.)

C

The C version uses data[mid] without any check — it compiles directly to mov rax, [rdi + rax*8]. No cmp, no jump, no extra block.

At O0, C has 9 basic blocks. At O2, it has 8 blocks. The structure barely changes because there's nothing extra to optimize away. (DWARF maps 9/9 O0 blocks to source lines.)

Ownership & Move: om_03 — Partition a Vec into evens and odds

What is this feature?

In Rust, when you pass a Vec to a function, the ownership moves. The caller can no longer use it. The compiler enforces this at compile time, and at the binary level, it means the function is responsible for eventually freeing the memory.

In C, you pass a pointer. The caller and callee both have access. You must manually remember to call free(). There's no compiler enforcement.

How does this affect the binary? Let's look at om_03, which takes a Vec/array and splits it into even and odd numbers.

/// Partition vec into two owned vecs (even/odd), consume original
#[inline(never)]
fn om_03(data: Vec<u64>) -> (Vec<u64>, Vec<u64>) {
    let mut evens = Vec::new();
    let mut odds = Vec::new();
    for val in data.into_iter() {
        if val % 2 == 0 { evens.push(val); }
        else { odds.push(val); }
    }
    (evens, odds)
    // original data consumed by into_iter
}

/* Partition into evens and odds */
NOINLINE void om_03(uint64_t *data, size_t n,
                    uint64_t **evens, size_t *ne, uint64_t **odds, size_t *no) {
    *evens = malloc(n * 8); *odds = malloc(n * 8);
    *ne = 0; *no = 0;
    for (size_t i = 0; i < n; i++) {
        if (data[i] % 2 == 0) (*evens)[(*ne)++] = data[i];
        else (*odds)[(*no)++] = data[i];
    }
    free(data);
}

Drop Glue: dg_11 — Build and tear down a HashMap of String→Vec

What is this feature?

When a Rust variable goes out of scope, the compiler automatically generates "drop glue" — code that frees all owned memory. For a HashMap<String, Vec<u64>>, this means recursively freeing every String key, every Vec value, and the HashMap itself.

In C, you must manually write nested free loops: free each value array, free each key string, then free the hash table structure.

The key difference at the binary level: Rust generates many small drop_in_place<T> call blocks. C has explicit free() calls mixed into the normal code flow.

/// HashMap<String, Vec<u64>> — double-nested drop
#[inline(never)]
fn dg_11(n: usize) -> u64 {
    let mut map: HashMap<String, Vec<u64>> = HashMap::new();
    for i in 0..n {
        let key = format!("key_{}", i % 5);
        map.entry(key).or_insert_with(Vec::new).push(i as u64);
    }
    let mut total = 0u64;
    for (key, vals) in &map {
        total = total.wrapping_add(key.len() as u64);
        for &v in vals {
            total = total.wrapping_add(v);
        }
    }
    total
    // map: HashMap<String, Vec<u64>> dropped
}

/* Map of string to values */
NOINLINE uint64_t dg_11(size_t n) {
    char *keys[256]; uint64_t *vals[256]; size_t vlens[256] = {0};
    size_t nk = 0;
    for (size_t i = 0; i < 5 && nk < 256; i++) {
        char buf[32]; snprintf(buf, 32, "key_%zu", i);
        keys[nk] = strdup(buf); vals[nk] = malloc(n * 8); vlens[nk] = 0; nk++;
    }
    for (size_t i = 0; i < n; i++) {
        size_t bucket = i % 5;
        vals[bucket][vlens[bucket]++] = i;
    }
    uint64_t total = 0;
    for (size_t i = 0; i < nk; i++) {
        total += strlen(keys[i]);
        for (size_t j = 0; j < vlens[i]; j++) total += vals[i][j];
        free(keys[i]); free(vals[i]);
    }
    return total;
}

? Operator: qm_07 — Parse comma-separated words from a string

What is this feature?

Rust's ? operator propagates errors automatically. When you write value.parse::<u64>()?, the compiler generates code that:

  1. Calls parse()
  2. Checks the discriminant: was it Ok or Err?
  3. If Ok: extract the value and continue
  4. If Err: immediately return the error to the caller

Each ? creates a branch point — a basic block that checks success/failure. In C, the equivalent is if (ret < 0) return -1;

/// Chain of string operations with ?
#[inline(never)]
fn qm_07(s: &str) -> Option<u64> {
    let first_word = s.split_whitespace().next()?;
    let last_word = s.split_whitespace().last()?;
    let first_char = first_word.chars().next()?;
    let last_char = last_word.chars().last()?;
    let sum = first_char as u64 + last_char as u64;
    let mid_word = s.split_whitespace().nth(s.split_whitespace().count() / 2)?;
    let mid_len = mid_word.len() as u64;
    Some(sum.wrapping_mul(mid_len))
}

Key Findings

C code is significantly easier to match than Rust across all 3 methods and all 5 features.

MethodRust (avg)C (avg)Gap
Value-based7%48% +41%

Across 300 individual comparisons (100 pairs × 3 methods), C wins 288, Rust wins 9, and 3 are ties (same accuracy).

Why? Two reinforcing factors:

  1. More blocks = more confusion. Rust averages 33 O0 blocks per function vs C's 14. The extra blocks (bounds checks, panic paths, drop glue, discriminant checks) create a larger cost matrix for Hungarian matching, with more opportunities for wrong pairings.
  2. Optimization hits harder. The extra blocks exist because of Rust's safety guarantees. At O2, the compiler eliminates, inlines, or merges many of them — dramatically changing the block structure. C has fewer "extra" blocks to begin with, so its O0→O2 transformation is gentler.
